# Пробный перенос JSON в PostgreSQL

API поддерживает два режима: `STORAGE_BACKEND=json` (по умолчанию) и
`STORAGE_BACKEND=postgres`. Наличие `DATABASE_URL` само по себе ничего не
переключает. Импорт и переключение не запускаются автоматически при обновлении.

Перенос сохраняет весь документ в `cargona_legacy_state.document` (JSONB), включая
неизвестные поля, историю, денежные операции, признаки веса и квитанции повторных
запросов. ID, суммы, даты, пароли и токены не пересчитываются. Нормализованная
Drizzle-схема пока не используется: она не описывает все поля рабочего JSON.

## Проверка копии

Сначала получите согласованную копию `cargona-store.json`. Для финального импорта
потребуется остановить все процессы, которые его меняют. Для репетиции используйте
отдельную тестовую PostgreSQL-базу и копию, а не живой файл. Копия содержит секреты;
храните её с ограниченными правами и не добавляйте в Git.

После сборки CLI находится в `apps/api/dist/state-migration.mjs`, в образе API —
по тому же пути относительно `/app`. Передайте `DATABASE_URL` через окружение;
не вставляйте пароль в аргументы команды.

```sh
node apps/api/dist/state-migration.mjs inspect /backup/cargona-store.json
node apps/api/dist/state-migration.mjs trial /backup/cargona-store.json
```

`inspect` не подключается к БД. `trial` создаёт таблицу и вставляет документ внутри
транзакции, читает его обратно, сверяет SHA-256 и откатывает транзакцию, включая
создание новой таблицы. Отчёт содержит только режим, количества записей по
коллекциям и SHA-256; порядок ключей JSON не влияет на хеш. Совпадение хеша
проверяет все значения, а не только количества. Существующее состояние в таблице
никогда не заменяется. Некорректный JSON или повторные ID останавливают перенос.

## Репетиция сохранения и обратного экспорта

Только в отдельной тестовой БД, после остановки источника копии:

```sh
node apps/api/dist/state-migration.mjs import /backup/cargona-store.json --confirm-stopped
node apps/api/dist/state-migration.mjs export /backup/roundtrip.json
node apps/api/dist/state-migration.mjs inspect /backup/roundtrip.json
```

Сравните хеши и количества исходника и экспорта. Импорт коммитится только после
сверки чтением обратно. Повторный импорт отклоняется; экспорт не перезаписывает
существующие файлы и на Unix создаётся с правами `0600`. Права Windows определяет
ACL каталога. Экспорт не следует автоматически подставлять вместо рабочей базы.

`--confirm-stopped` — явное подтверждение оператора, а не автоматическая проверка
остановки API. Между копированием и окончательным переключением JSON может
измениться; окончательный перенос потребует новой копии при остановленных
записях. Восстановление за два часа требует отдельной репетиции резервного восстановления.

Локальная проверка: `node scripts/state-migration.test.mjs` после сборки DB.
Она использует двойник транзакций. Для проверки драйвера, SQL и прав PostgreSQL
обязательно выполните репетицию на реальной отдельной БД перед переключением.
Для автоматической проверки SQL можно передать тесту `MIGRATION_TEST_DATABASE_URL`
с адресом пустой одноразовой БД: он выполнит реальную пробную транзакцию и
проверит, что создание таблицы откатилось. Рабочую БД для этого не используйте.

## Режим API и переключение

`STORAGE_BACKEND=postgres` загружает только заранее импортированное состояние.
При пустой БД, неверном хеше, недоступном PostgreSQL или втором писателе API
не стартует. Автоматического импорта, создания пустой базы и возврата к JSON нет.
В этом режиме рабочий JSON не читается и не обновляется.

Один процесс API держит блокировку PostgreSQL на всё время работы. Запросы и
фоновые изменения рассылки выполняются последовательно. Ответ на запрос
сохранения ждёт COMMIT. Запись обновляет документ, хеш и ревизию в одной
транзакции; несовпадение ревизии, потеря соединения или ошибка записи блокируют
дальнейший доступ до перезапуска и проверки состояния. `/health/ready` проверяет
доступность хранилища. Импортёр также подключается к выбранному хранилищу;
в режиме PostgreSQL работающий API необходимо остановить перед отдельным CLI-импортом.

Сейчас это одна JSONB-строка и один процесс API: горизонтальное масштабирование
не поддерживается, длинные запросы могут задерживать остальные. Сначала требуется
проверка на объёме реальной копии данных; нормализованные таблицы и параллельные
записи потребуют отдельного изменения модели хранения.

После успешной репетиции в согласованное окно оператор:

1. Останавливает API и другие процессы записи. Сохраняет окончательную копию JSON.
2. Выполняет `inspect`, `trial`, затем `import --confirm-stopped` в пустое целевое
   хранилище. Сверяет обратный экспорт с окончательной копией.
3. Устанавливает `STORAGE_BACKEND=postgres` в окружении Compose и запускает API.
4. Проверяет `/health/ready`, клиентов, посылки, финансовый журнал, создание записи
   и её сохранность после перезапуска API. После этого открывает доступ клиентам.

Откат до новых записей: остановить API и вернуть режим `json` с исходной копией.
После новых записей в PostgreSQL старый JSON уже устарел: сначала остановить API,
экспортировать актуальное состояние в новый файл, проверить хеш и заменить JSON
при остановленных процессах. Простое переключение переменной после работы в
PostgreSQL потеряет новые данные. Серверные действия выполняет оператор;
в обновлении исходников переключение не производится.

Проверка режима: `node scripts/postgres-runtime.test.mjs` после сборки DB/API.
По умолчанию проверяются реальное хранилище API с двойником БД и Fastify.
При передаче `MIGRATION_TEST_DATABASE_URL` дополнительно проверяются SQL,
сохранение после повторного подключения, запрет второго писателя и ревизии.
Этот дополнительный тест создаёт и удаляет свою таблицу в пустой одноразовой БД.

CI выполняет эти тесты на отдельном PostgreSQL 16 перед публикацией Docker-образов.
Настройка webhook при старте также сохраняет очередь обновлений Telegram:
предварительное удаление webhook со сбросом сообщений убрано.
