# Обновление и откат приложения

Новые команды CLI обновляют Docker-образы, а не Git checkout. Сборка на сервере,
`git reset --hard`, очистка образов и автоматические миграции не выполняются.
Нужны Docker Compose v2, Bash, util-linux (`flock`), coreutils и опубликованные
образы всех трёх сервисов. Образы API теперь содержат описание совместимости.
Это ещё не установка автономного Compose-комплекта: CLI, `release.sh`,
`update.sh` и конфиги должны быть заранее установлены оператором.

```sh
cargona backup
cargona update <полный SHA коммита из успешной сборки GitHub>
cargona rollback:list
cargona rollback <release-ID из списка>
```

По умолчанию используются `ghcr.io/skellyva/cargona-api`, `cargona-web` и
`cargona-bot`. Для другого владельца установите `CARGONA_IMAGE_OWNER` в окружении
команды. Образы должны быть доступны для `docker pull`; для закрытого registry
оператор заранее выполняет вход. `latest` не принимается: нужны все 40 символов
SHA. Скачанные образы закрепляются по локальным image ID, чтобы повторная
публикация тега не меняла запущенную версию.

Перед простоем CLI скачивает все образы и проверяет совместимость API. Затем
сохраняет старые образы отдельными Docker-тегами, разрешённый Compose-конфиг,
настройки и список работавших сервисов. Проверяет, что режим хранилища и его
адрес в Compose соответствуют работающему API. Обновление не может одновременно
переключать JSON/PostgreSQL или путь к базе.

На время бэкапа и проверки останавливаются backend, frontend, bot и Caddy:
внешний доступ закрыт. JSON копируется после остановки записи, проверяются
структура и версия формата. Для PostgreSQL создаются `pg_dump -Fc`, список
содержимого через `pg_restore --list` и проверенный JSON-экспорт состояния.
Поддерживается PostgreSQL в сервисе `postgres`, который использует backend;
для внешней БД нужен отдельный процесс резервирования. Для файлов вычисляется
SHA-256. Неудачный бэкап не допускает запуск новых образов.

После запуска нового API CLI до двух минут ждёт `/health/ready`. Только после
успеха запускает ранее работавшие frontend и bot, затем Caddy. Активные image ID
сохраняются в `data/releases/active.yml`; команды CLI учитывают этот файл.
При ручном использовании Compose добавляйте его вторым файлом:

```sh
docker compose -f docker-compose.yml -f data/releases/active.yml ps
```

Откат приложения сначала создаёт свежую точку восстановления, затем запускает
сохранённые образы с их конфигом. **База остаётся актуальной**: старый бэкап
автоматически не подставляется. После отката новые данные по-прежнему доступны,
а свежая точка содержит версию, с которой откатывались. Совместимость должна
быть объявлена образом; описание не заменяет репетицию на реальной копии.
При несовместимом изменении модели данных разработчик должен менять
`storageFormat` и декларацию API. Старый API откажется загружать неизвестный
формат; неизвестные дополнительные поля совместимого формата сохраняются.

При ошибке нового запуска CLI пытается вернуть прежние совместимые образы,
проверить API и открыть доступ. Если прежний образ не объявляет совместимость
или восстановление не проходит проверку, сервисы остаются остановленными.
Команда завершается ошибкой и сообщает расположение точки восстановления.
Старые исторические образы без декларации нельзя считать автоматически
проверенными: перед первой новой установкой сохраните бэкап и отрепетируйте
возврат с оператором. После неудачи не включайте Caddy до выяснения состояния.

Точки находятся в `data/releases/release-*`, каталог доступен только владельцу,
файлы создаются с закрытыми правами. Конфиг и JSON содержат пароли/токены:
не публикуйте каталог и не отправляйте его в Git. Теги `cargona-release-*`
удерживают старые образы; ручная очистка Docker может уничтожить возможность
отката. Автоматической ротации пока нет — следите за местом на диске.

Это локальные бэкапы перед обновлением. Зашифрованные автобэкапы вне сервера,
проверка полного `pg_restore`, автоматическая установка CLI/конфигов и
репетиция восстановления на копии реальных данных остаются следующими этапами.
`pg_restore --list` проверяет читаемость архива, а не успешность восстановления
всех таблиц. RPO/RTO пока не подтверждены.

Проверки скриптов: `node scripts/release.test.mjs` (Docker заменён двойником)
и `for script in release.sh update.sh cargona; do bash -n "$script"; done`. CI дополнительно проверяет API на
PostgreSQL 16. Ни одна из этих команд тестов не подключается к рабочему серверу.
