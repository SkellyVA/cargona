# Работа без репозитория на сервере

Новая установка использует только опубликованные Docker-образы одной версии, Compose, Caddyfile, init-db.sql, CLI и скрипты обслуживания. Node/pnpm/Git и исходники приложения на сервере не требуются. Нужны Linux, Docker Compose v2, Bash, curl, openssl, util-linux; Restic и systemd нужны для автобэкапов.

```bash
# Скачайте install.sh из доверенной версии и проверьте файл перед запуском.
bash install.sh FULL_40_CHARACTER_GIT_SHA /opt/cargona
cd /opt/cargona
docker compose pull
docker compose up -d
cargona status
```

Версия должна иметь успешно опубликованные образы API/web/bot в GHCR. Установщик требует пустой каталог, не изменяет существующие данные, не запускает Docker и создаёт случайные секреты в закрытом `.env`. Пароль администратора следует забрать из `.env` по SSH и сохранить в менеджере паролей. Для закрытых образов оператор предварительно выполняет `docker login ghcr.io`.

Обновление приложения — `cargona update SHA`; сохранённые предыдущие образы и копия дают возможность `cargona rollback ID`. Скрипты CLI обновляются отдельной командой `cargona tools:update SHA`: скачивание всех файлов и проверка Bash заканчиваются перед заменой, права исполнения выставляются заново, предыдущие скрипты остаются в `data/tools/previous-*`. Рабочий Compose, `.env`, Caddyfile и данные не заменяются. При прерывании замены скриптов восстановите предыдущий набор вручную из этого каталога перед следующими действиями. Не удаляйте нужные точки и Docker-теги отката.

Для перехода существующей установки нельзя запускать установщик поверх неё. Сохраните локальную и внешнюю копию; проверьте имена Compose-проекта, реальные mounts и `.env`; в окно обслуживания замените только Compose на runtime-вариант с той же версией образов и сохранёнными путями. Не запускайте параллельно второй API. Эта операция не выполняется автоматически. Переключение JSON/PostgreSQL — отдельная процедура из [postgres-migration.md](postgres-migration.md).

Сброс пароля владельца и импорт через CLI теперь делают согласованную копию, останавливают API и внешние сервисы, затем запускают отдельный процесс записи в том же хранилище. После завершения возвращают доступ только после успешной readiness-проверки. Пароль вводится скрыто, сохраняется хешем, старые сессии компании отзываются. JSON больше не редактируется через shell-строку с паролем; импорт в работающий API через независимый writer запрещён. В режиме PostgreSQL сохранение проходит через тот же механизм ревизии и блокировки. Ошибка команды не объявляется успехом; автоматического возврата старых данных нет.

## Проверка восстановления

```bash
cargona offsite:list
cargona offsite:restore SNAPSHOT_ID
# Найдите каталог с checksum/storage внутри нового data/offsite/restored-*.
cargona rehearse /absolute/path/to/snapshot ghcr.io/skellyva/cargona-api:SHA
```

Для локальной точки также можно использовать `data/releases/release-*`. Образ API и postgres:16-alpine должны быть доступны локально; Docker может загрузить postgres из registry при отсутствии. Команда создаёт новую internal-only Docker-сеть и одноразовую PostgreSQL без опубликованных портов, восстанавливает дамп целиком (`pg_restore --exit-on-error`) либо проверяет JSON → trial/import → export, сверяет хеши и запускает API с перезапуском. Telegram и другие внешние сервисы из этой сети недоступны. Рабочая Compose-база не используется. Созданные контейнеры, тома и сеть удаляются при завершении; копии и отчёт остаются в закрытом `data/rehearsals/check-*`. Это место содержит персональные данные и секреты.

Восстановление в production выполняет оператор в согласованное окно после успешной репетиции. Простой возврат старого JSON после работы PostgreSQL потеряет новые записи. Резервный образ должен быть доступен в GHCR или локальном архиве: offsite-копия не содержит Docker-образов.

## Мониторинг

```bash
cargona monitor:configure  # отдельный бот и положительный ID личного чата
cargona monitor:run
cargona monitor:enable
cargona monitor:status
```

Проверки каждые две минуты: API/хранилище, активные bot webhooks через read-only getWebhookInfo, очередь Telegram и свежие ошибки, контейнеры backend/frontend/caddy и OOM, свободное место (<1 GiB), память (<64 MiB), отсутствие внешней копии за 30 минут и ошибка последней попытки. Уведомления отправляются при изменении списка проблем и восстановлении; неудачная отправка повторяется. Групповые чаты не поддерживаются. Секреты и данные клиентов в сообщение не включаются. `/health/bots` доступен только с loopback внутри API; публичные proxy-запросы не вызывают Telegram API.

Без настройки Telegram проверки доступны в журнале systemd, уведомлений нет. Полная остановка сервера не может быть обнаружена внутренним таймером: нужен отдельный внешний uptime-monitor оператора. Авария Telegram также мешает доставке уведомлений по этому каналу. Новые мониторинг и бэкапы не включаются обновлением автоматически.

Копия production-базы и ключи B2 не передавались, поэтому SLA/RPO/RTO и время реального переключения ещё не подтверждены. Технические проверки выполняются на синтетических данных; финальную репетицию на реальном объёме оператор запускает отдельно.
